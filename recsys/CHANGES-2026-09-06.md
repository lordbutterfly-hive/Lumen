## Review fixes applied (2026-09-06, second pass)

1. **sslmode host-check.** `_pool_connect` no longer forces `sslmode=disable` unconditionally — it calls `_sslmode_disable_dsn_if_loopback(dsn)`, which parses the DSN (`psycopg.conninfo.conninfo_to_dict`) and only injects `sslmode=disable` when the host is `127.0.0.1`/`::1`/`localhost` AND no `sslmode` is already present; an unparseable DSN passes through unmodified (fail safe). **Verified live via `docker inspect` on the box**: the running container uses `--network host`, and `RECSYS_DATABASE_URL`/`LUMEN_LITE_DATABASE_URL` point at `127.0.0.1` — the loopback branch is what actually fires in production today. `deploy/compose.recsys.yml`'s bridge-network shape (where a Postgres on a different host would be plausible) is not what runs on the box.
2. **Single-flight: bounded wait + fresh exception per waiter.** `_SingleFlight.run` now takes `wait_timeout_s` (from `ServiceConfig.single_flight_wait_s`, default 20s); a waiter that times out raises `_SingleFlightTimeout`, which `build_feed` turns into `FeedUnavailableError(kind="single_flight_timeout")` — a fast, clear 503, not an independent second build (chosen over the alternative because piling a second build onto an already-stalled mirror makes the underlying problem worse, and the frontend already tolerates a slow/absent `/feed` by serving stored/trending). Each waiter now gets `_clone_exception(entry.error)` — a fresh object with the same data — not the same shared instance; `copy.copy()` was tried first and rejected because it reconstructs via `type(exc)(*exc.args)`, which crashes for `FeedUnavailableError` (its `__init__` takes more parameters than it forwards to `super().__init__`).
3. **Pool sizing + exhaustion fallback.** `RECSYS_LOCAL_POOL_MIN`/`MAX` defaults changed from 1/3 to 2/16 (matching `RECSYS_MAX_CONCURRENT_REQUESTS`'s ceiling) — reproduced offline: 3 was a self-inflicted exhaustion under realistic concurrency. `_fetch_rows` in both `lite_engagement.py` and `seen_log.py` now catches `HafsqlUnavailableError` from `pool.borrow()` and falls back to one direct, unpooled connection for that call (today's pre-L1 behaviour) instead of letting it propagate into the caller's own `except Exception`, which degraded to `{}` (no lite engagement / no suppression) — a real signal loss for a condition a single connection can usually still answer.

   **★ THIRD REVIEW FIX (2026-09-06), further narrowed.** That blanket `except HafsqlUnavailableError` was itself wrong: `_ConnPool.borrow()` raises the same exception class for genuine pool exhaustion (every slot in use, none released in time — the DB is presumably fine) AND for the breaker being OPEN (the last several connect attempts failed — the DB is presumably NOT fine). Falling back to a direct connect on breaker-open just retries a database already proven down, one call at a time, defeating the breaker's entire purpose. `_ConnPool.borrow()`'s exhaustion path now raises a new `PoolExhaustedError(HafsqlUnavailableError)` instead — a subclass, so existing `except HafsqlUnavailableError` callers that do not care about the distinction are unaffected — and `_fetch_rows` in both files catches `PoolExhaustedError` (fall back to direct connect) BEFORE the broader `HafsqlUnavailableError` (breaker open: re-raise, fast-fail). The exhaustion-fallback WARNING is also now throttled to at most once per `_BREAKER_COOLDOWN_S` (30s) per DSN instead of once per call, so a sustained exhaustion does not write one WARNING per request for as long as it lasts. `RECSYS_LOCAL_POOL_MAX` also dropped from 16 to 6 in this same pass — see its own table row above for why (the idle-reaper gap this uncovered).
4. **Per-lane isolation in `pipeline.py`.** New `_lane_or_empty(name, viewer_account, fn, default)` helper wraps `gather_candidates`'s five direct gateway calls (`in_network_posts` x2 — the in-network lane and the OON_ALS lane, `engaged_oon_posts`, `popular_posts`, and the popular lane's `reputations_for` call). Before this, C1's tighter 10s default meant a lane that would have SUCCEEDED at, say, 12s under the old 900s ceiling now 503'd the WHOLE feed instead of just going missing. The `reputations_for` case was worse than a regression risk — the surrounding comment already PROMISED "a gateway that cannot answer ... must give an unranked-by-reputation lane, never no feed at all," but the only guard in place (`getattr`/`callable`) covered a gateway that does not IMPLEMENT the method, not one that raises when called; that promise was never actually enforced against a real timeout.

   **★ THIRD REVIEW FIX (2026-09-06) — the residual gap flagged above is now closed.** Three more request-path calls had no lane guard at all: `interest_candidates`/`established_interest_candidates` (both call `gateway.tag_posts`, and one of the two runs for EVERY viewer, cold or established — the widest-reach gap of the three), `popular_fallback` (a starved viewer's own padding, inside `_fallback_filler`), and `second_degree_engagers` (the vouch-gate lookup inside `rank_feed`). All three are now wrapped in the same `_lane_or_empty`, degrading to an empty lane/dict with one WARNING instead of a 503 for the whole feed. `_lane_or_empty` itself also changed in this pass: it used to catch bare `Exception`, which silently emptied a lane on a genuine programmer bug (`TypeError`/`KeyError`/`AttributeError`/`NameError`) instead of failing loudly, and wrote a full traceback per lane per request for as long as a stall lasted. It now re-raises those four programmer-error types, and keeps the traceback only for the first failure per lane per process — later failures for the same lane log a one-line WARNING with a running count.
5. **Q2 NULL-safety.** Both EXISTS clauses in `_SQL_ENGAGED_OON_POSTS_V2` changed from a bare `col >= %(since)s` to `(col IS NULL OR col >= %(since)s)`. SQL's three-valued logic makes `NULL >= x` evaluate to NULL (not true), so the bare form would silently drop a NULL-timestamped reblog/reply row that the UNBOUNDED V1 query kept — breaking the identical-result-set equivalence Q2 depends on. Whether `hafsql.reblogs.created_at` / `operation_comment_view."timestamp"` can ever be NULL could not be checked against the live mirror this session; the NULL-safe form is used unconditionally rather than assumed away.
6. **Q1 fallback + a wrong comment.** The V2 path's client-side filter now normalizes BOTH sides to naive before comparing (so an unexpectedly-aware timestamp from the mirror is handled correctly, not a crash) — and, as defense in depth for a genuinely structural break (e.g. the mirror's view losing its `id` column), a failure inside the V2 fetch itself now falls back to running the V1 query for that same call, logging one ERROR for the life of the process, instead of the old behaviour: the single outer `except Exception` caught it and silently degraded every viewer to own-posts-only tags forever, with only a per-request WARNING. Separately, the equivalence comment's justification for the "fewer than `limit` in the window" case was corrected — it previously claimed "an account can only have fewer than `limit` votes TOTAL in that case," which is false (a long-inactive account routinely has thousands of votes total and few inside a short recent window); the real argument is the one about `id`/time correlation, now spelled out.

   **★ THIRD REVIEW FIX (2026-09-06), two more bugs in this same fallback.** First: the "logged once" flag (`_v2_fallback_logged`, renamed `_v2_disabled_for_process`) gated only the log line — the call site's `use_v1` was a fresh local recomputed from `_vote_history_v2_enabled()` on every single call, so a structural failure discovered on request #1 logged its ERROR once and then went right back to attempting (and re-failing) V2 on every subsequent request for the rest of the process, silently paying the V2-then-V1 double-query cost every time instead of once. `use_v1`'s own initial computation now ORs the process-wide flag in, so the first structural failure disables V2 for the rest of the process, matching what the log message already claimed. Second: the inner `except Exception` around the V2 fetch also caught `psycopg.errors.QueryCanceled` (a statement-timeout cancel) and treated it as "structural," falling back to V1 — but a timeout is not a structural break, it's the SAME operational condition V1's own query is equally exposed to, so retrying with V1 paid BOTH queries' timeout budgets, up to 12s, on exactly the accounts Q1 targets (real, active voters — the ones the old blocks-backward V1 scan was already slow for). `psycopg.OperationalError` (which `QueryCanceled` subclasses) is now re-raised instead, propagating to the existing outer `except Exception`, which already degrades to own-posts-only tags for exactly this case.

7. **★★★★ FOURTH REVIEW FIX (2026-09-06) — item 4's closure claim above was FALSE; the gap was live in production.** A full-stack review found `_suppressed` (`pipeline.py`, wraps `gateway.suppressed_keys`, which carries `_request_statement_timeout_ms` — `io/hafsql.py` around line 3175) called at BOTH its call sites OUTSIDE any `_lane_or_empty` guard: once in `rank_feed` (`suppressed = _suppressed(gateway, candidates)`, a bare assignment that runs for **every** feed, gated by nothing), and once in `_fallback_filler` (`suppressed=_suppressed(gateway, fallback)`, inline inside a `filter_eligible(...)` keyword argument, reached whenever a viewer's own pool is starved). The third review fix's own sweep missed both because they are not their own guarded statement the way every other lane is — one is a plain `x = f(...)` line, the other sits inline as a kwarg — which is exactly the shape a text grep for `_lane_or_empty` call sites walks past. With `RECSYS_REQUEST_STATEMENT_TIMEOUT_MS` unset on the box (10000ms default in force), a single cancelled `suppressed_keys` query turned into a 503 for the WHOLE feed, plus a full, unthrottled traceback per request for as long as the mirror stayed slow.

   Both are now wrapped the same way as every other lane: `suppressed: frozenset[str] = _lane_or_empty("suppressed", viewer.account, lambda: _suppressed(gateway, candidates), frozenset())` in `rank_feed`, and `_lane_or_empty("suppressed_fallback", viewer.account, lambda: _suppressed(gateway, fallback), frozenset())` in `_fallback_filler`. Degrading to `frozenset()` means `filter_eligible` treats the batch as unsuppressed — a reader may see a post already covered by a §8.7 moderation report, which is strictly better than the whole feed (or the padding) failing outright — with the same once-per-lane-per-process traceback throttling every other lane already gets.

   **The audit this required** (every call in `pipeline.py` that can reach a query carrying `_request_statement_timeout_ms`, file:line, and its guard):

## One deliberate deviation from the map's literal text (unchanged from the first pass)

L1 does not re-assert `SET statement_timeout` per query the way the map suggests for the mirror (which sits behind an external transaction pooler proven to revert `SET`s issued at connect time). Lumen's local Postgres is a direct, un-pooled session with no evidence of a pooler in front of it, so that specific failure mode does not apply; the existing one-time-per-physical-connection `SET` (predating this build) is kept.

## Rollback

Every item has an independent kill switch — no redeploy is required to revert any one of them:

1. **Fastest**: set the corresponding env var to a kill value in `/opt/lumen/recsys.env` and restart the container (`RECSYS_VOTE_HISTORY_V2=off`, `RECSYS_OON_TIME_BOUND=off`, `RECSYS_LOCAL_POOL=off`, `RECSYS_SINGLE_FLIGHT=off`, `RECSYS_REQUEST_STATEMENT_TIMEOUT_MS=0` — any subset, independently). The per-lane isolation in `pipeline.py` (review fix 4) has NO flag — it is unconditional degrade-to-empty-on-failure behaviour, considered safe enough to ship without one; reverting it requires the full image rollback below.
2. **Any restart costs up to ~20.7 minutes of refused/degraded `/feed`, worst case.** Per the build map's own measurement (section 6): the MEASURED worst case is 1242s (20.7 min), which is what compose's healthcheck `start_period` of 1800s is sized to cover. (An earlier draft of this section understated this as "~6.5 minutes" — wrong; the 6.5-minute figure was a typical-case number, not the worst case this section is about, and it is not repeated here.) During warm-up the port is closed, `/feed` fails fast client-side (`RECSYS_FAST_FAIL_MS`), readers get stored feeds or trending, and the warmer skips cycles. A flag flip that requires a restart is not free — batch the flags you intend to flip into one restart rather than restarting once per flag.
3. **Full revert**: redeploy the previous image tag (`recsys:v8-20260827` per the map's section 6) — this source tree is not built into an image by this task; the running container is untouched. **Do not** `docker tag recsys:v9-YYYYMMDD recsys:v8-20260827` as a shortcut for anything — it overwrites the `v8-20260827` tag with the new image, destroying the exact rollback target step 8 of the map's own procedure depends on. If a new tag needs to reach the trust-batch systemd unit, edit `/etc/systemd/system/lumen-trust.service` line 12 (which currently references `recsys:v8-20260827` by name) and `systemctl daemon-reload` — the map's own preferred option — rather than retagging.
